Project Overview

CADformer addresses a fundamental gap in LLM-based program synthesis: while large language models have become capable at generating general executable code, they struggle with CAD geometry creation, which demands more than just runnable output. An input like "create a hollow beam with a certain wall thickness and bolt pattern" requires splitting into discrete modeling decisions — creating solid shapes, removing material, placing repeated features — where mistakes don't cause runtime errors but instead produce geometrically incorrect shapes that execute without complaint. Existing approaches like direct generation and chain-of-thought prompting treat the full request as a single generation task, leaving the model to track complex spatial relationships and dimensional dependencies without any structural grounding.

CADformer combines ideas from three complementary NLP papers — Toolformer, DECINT, and Gorilla — into a single five-stage pipeline purpose-built for the CAD domain. From DECINT, it borrows interleaved decomposition: rather than planning in natural language and generating code only at the end (as chain-of-thought does), CADformer generates one natural-language sub-step and its corresponding code fragment together, so each future step is grounded in the actual current program state rather than a textual description of it. From Gorilla, it borrows retrieval-augmented generation: for each sub-step, a BM25 index retrieves the most relevant CadQuery API documentation from a library of 34 elementary operations, grounding code generation in valid syntax and preventing the hallucinated selector strings and invalid argument combinations that plague direct generation approaches.

Pipeline Architecture

Stage 1/2 — Preprocessing & Normalization

The input natural-language CAD request is preprocessed by normalizing units and resolving any missing or implied dimensions before any decomposition or code generation begins. This step ensures that ambiguous or incomplete geometric specifications — such as an unspecified wall thickness or an implied symmetry — are made explicit before they propagate into downstream modeling steps where a wrong assumption would cascade through the entire program.

Stage 3 — BM25 Retrieval

For each decomposed sub-step, CADformer retrieves the top three most relevant elementary operations from a hand-curated library of 34 CadQuery operations using BM25 keyword search. The library covers five categories — primitive creation, boolean operations, transforms, feature operations, and pattern operations — with each entry containing the operation name, function signature, natural-language description, allowable constraints, and a worked example. The retrieved documentation is injected directly into the code generation prompt in the style of Gorilla's retrieval-aware generation, grounding each step in valid CadQuery syntax. This retrieval step proved to be the single largest performance driver in the system: removing it (CADformer-NoRetr) dropped execution success rate from 86.1% to 52.8%, a 33.3 percentage point gap that actually exceeded Gorilla's reported 12–23% hallucination reduction from retrieval — suggesting that CadQuery's selector syntax and operation chaining are harder for a model to recall from memory than standard ML API names.

Stage 4 — Code Generation

For each sub-step, the code generation model receives the original full request, all prior natural-language sub-steps, all prior generated code fragments, and the three retrieved CadQuery documentation entries. GPT-4 via the Azure OpenAI API serves as the underlying model for both decomposition and code generation. A key addition specific to the CAD domain is a continuously updated context summary injected into each prompt, listing every variable created so far alongside its inferred geometric type — solid, face, edge, or wire. This directly addresses a common failure mode in NL-to-CAD generation where a model applies an operation to the wrong geometric object type, a class of error that produces no runtime exception but yields incorrect geometry. Intermediate steps use explicit named references (s1, s2, etc.) so later steps can refer to prior geometry unambiguously, such as "the top face of the box from s1."

Stage 5 — Execution & Validation

Once all sub-steps have generated code fragments, the pieces are assembled into a full CadQuery Python script and executed. The system records whether execution succeeds or fails, and surfaces warnings and errors at the step level so failures can be traced to their origin sub-step rather than the assembled program as a whole. Failure analysis across the benchmark revealed three dominant failure modes: invalid selector syntax where the model generates selectors like "|Z and >Z'" that are syntactically plausible but violate CadQuery's selector grammar (analogous to the API hallucination problem Gorilla addresses); ordering violations where a geometrically correct operation is placed before a prerequisite boolean operation has created the relevant geometry; and output formatting errors in the non-CADformer baselines where the model wraps generated code in markdown fences, causing immediate parse failures. Execution Success Rate (ESR) — whether the assembled program runs without error — was the primary evaluation metric across all four methods tested on CADBench, a 36-prompt benchmark spanning three difficulty tiers.
